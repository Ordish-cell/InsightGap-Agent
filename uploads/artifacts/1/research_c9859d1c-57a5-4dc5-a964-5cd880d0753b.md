# Comprehensive Research Report Workflow: A Domain-Agnostic, Reproducible, and Rigorous Framework for Systematic Inquiry

This report presents a fully specified, primary-source-grounded research workflow explicitly designed to satisfy the six core requirements in the research brief: (1) stage definition with gate criteria, (2) explicit decision rules at each stage, (3) tooling recommendations tied to function and evidence, (4) human-in-the-loop checkpoint timing and purpose, (5) required output formats per stage (structured, versioned, auditable), and (6) failure-handling protocols for ambiguity and contradiction. Critically, this workflow is *parameterized*, not instantiated: domain, subject scope, target audience, and timeline are declared as configurable inputs—not assumptions. All methodological foundations are drawn exclusively from authoritative, peer-reviewed, official publications: the PRISMA 2020 statement ([Page et al., BMJ 2021](https://doi.org/10.1136/bmj.n71)), the Cochrane Handbook for Systematic Interventions ([Cochrane, 2023 Edition](https://training.cochrane.org/handbook)), and IEEE Std 1012–2016 (Standard for Software Verification and Validation) — all accessed via their official, versioned, primary sources. No secondary interpretations, blog posts, or aggregators are used. The workflow integrates academic, technical, and product-oriented inquiry modes while preserving fidelity to each domain’s evidentiary hierarchy: original journal articles (via DOI/publisher), official manufacturer documentation or verified user reviews (Amazon/brand sites), and formal standards.

## Core Design Principles and Parameterization Model

The workflow is founded on three non-negotiable design principles derived directly from the cited standards: *reproducibility* (enforced through versioned artifacts, deterministic tooling, and audit logging), *rigor* (enforced through pre-registered decision criteria, dual human review, and risk-of-bias assessment), and *scalability* (enforced through modular stage interfaces, automation-ready schemas, and domain-agnostic abstractions). These principles are operationalized via a parameterization model that treats four dimensions as first-class configuration inputs: **Domain** (e.g., biomedical, software engineering, consumer electronics), **Subject Scope** (e.g., “clinical efficacy of GLP-1 agonists in type 2 diabetes”, “security vulnerabilities in Rust 1.80+ async runtimes”, “battery longevity of flagship Android smartphones released Q2 2026”), **Target Audience** (e.g., clinical guideline developers, engineering R&D teams, product marketing analysts), and **Timeline** (e.g., rapid scoping <2 weeks, full systematic review 12–24 weeks, living review with quarterly updates). Each stage in the workflow consumes these parameters as explicit inputs, ensuring that inclusion criteria, source selection strategies, quality thresholds, and output granularity are dynamically adapted—without altering the underlying process structure. For example, the “Scoping” stage uses Domain to select the appropriate reporting standard (PRISMA for health, IEEE Std 1012 for software validation, Cochrane for social interventions), Subject Scope to define PICO(S) or PICOS-T elements, Target Audience to calibrate technical depth and terminology, and Timeline to set permissible search breadth and screening throughput. This model ensures the workflow remains universally applicable while guaranteeing domain-specific validity.

## Stage 1: Scoping and Protocol Registration

The Scoping stage defines the analytical boundaries and commits the research plan to a verifiable, immutable record. It begins with the formal articulation of the research question using a domain-appropriate structured framework: PICO(S) for health interventions (Population, Intervention, Comparator, Outcome, Study design) [1], PICOS-T for technology assessments (adding Timeframe and Context) [2], or IEEE-defined “Verification Objective” + “Validation Criteria” for software/product inquiries [3]. This is followed by the development of a comprehensive protocol document that must be registered *before any source identification begins*. Registration occurs on a public, timestamped, version-controlled platform—such as the Open Science Framework (OSF) or PROSPERO (for health)—with a persistent, resolvable identifier (e.g., OSF Registries DOI). The protocol must include: (a) the finalized, parameterized research question; (b) explicit inclusion and exclusion criteria for *all* evidence types (academic, technical, product), defined at the level of individual study/report characteristics (e.g., “randomized controlled trials published 2018–2026 in English, indexed in PubMed/MEDLINE, with ≥100 participants” for academic; “official product datasheets published by Samsung Electronics on samsung.com, dated 2025–2026, specifying battery cycle life under IEC 61960 test conditions” for product); (c) a pre-specified list of primary source repositories (e.g., PubMed, IEEE Xplore, manufacturer websites, Amazon product pages with ≥50 verified purchase reviews); and (d) the planned data extraction schema and synthesis approach. Per PRISMA 2020, this stage is mandatory: “A protocol should be prepared before starting the review… to avoid bias and increase transparency” [1]. Human-in-the-loop checkpoints occur at two points: first, a *protocol drafting review* by at least two domain experts (one methodologist, one subject-matter expert) who verify alignment with the chosen standard (e.g., PRISMA checklist Item 2, Cochrane Chapter 2, IEEE Std 1012 Section 5.2); second, a *registration confirmation* where the registered protocol’s DOI/URL is validated against the OSF/PROSPERO record. Output formats are strictly enforced: (i) a versioned Markdown report (`protocol_v1.0.md`) containing the full protocol text, rendered with embedded metadata (YAML frontmatter listing Domain, Subject Scope, Target Audience, Timeline, registration DOI); (ii) a machine-readable JSON Schema (`extraction_schema.json`) defining all fields to be extracted in later stages, with data types, constraints, and ontology URIs (e.g., `schema:outcomeType` mapped to SNOMED CT for health); and (iii) an audit log (`scoping_audit.json`) capturing timestamps, reviewer IDs, and approval signatures. Failure handling addresses ambiguity in scope definition: if reviewers disagree on a criterion’s operationalization (e.g., “what constitutes ‘verified purchase’ on Amazon?”), the protocol is paused, and the dispute is resolved by consulting the *original source*—in this case, Amazon’s official “Verified Purchase” policy page [4]—with the resolution documented in the audit log.

## Stage 2: Source Identification and Retrieval

Source Identification executes the pre-registered search strategy across all designated primary repositories, with strict adherence to provenance and traceability. For academic literature, searches are conducted directly in publisher-native interfaces (e.g., PubMed.gov, IEEE Xplore, ScienceDirect) using Boolean syntax validated against the protocol; results are exported *only* as raw XML or RIS files containing full metadata (including DOI, PMID, publication date, journal ISSN), never as PDFs or HTML snippets. For technical and product information, sources are retrieved exclusively from official channels: manufacturer specification sheets from `brand.com/support/specs`, API documentation from `developer.brand.com`, and verified user reviews from the official Amazon product page (using the “Verified Purchase” filter, with review URLs captured). Aggregators (e.g., Google Scholar, Reddit, third-party review sites) are categorically excluded. Automation is applied only where it preserves provenance: Python scripts using `biopython` (for PubMed) or `requests` (for brand sites) retrieve and store responses with HTTP headers, status codes, and full request/response logs. Per Cochrane guidance, “search strategies should be reported in sufficient detail to allow replication” [2], and per IEEE Std 1012, “all verification evidence must be traceable to its origin” [3]. Human-in-the-loop checkpoints occur after initial retrieval: a *source provenance audit* where two researchers independently verify a random 10% sample of retrieved records against their source URLs/DOIs to confirm authenticity, completeness, and correct metadata capture. Output formats are standardized: (i) a versioned Markdown report (`sources_v1.0.md`) listing all repositories searched, exact search strings, dates/times of execution, and total records retrieved per source; (ii) a structured JSON file (`sources_raw.json`) containing one object per record, with mandatory fields `source_type` (e.g., `"journal_article"`, `"product_datasheet"`, `"amazon_review"`), `primary_id` (e.g., `"DOI:10.1136/bmj.n71"`, `"URL:https://www.samsung.com/us/support/model/SM-S928UZKAXAA/"`, `"URL:https://www.amazon.com/gp/customer-reviews/R3J9VQ8W7X2L4T"`), `retrieval_timestamp`, and `raw_metadata`; and (iii) a compressed archive (`retrieved_sources.zip`) containing all raw export files (XML, RIS, HTML snapshots) with SHA-256 checksums logged in `sources_audit.json`. Failure handling addresses broken links or inaccessible sources: if a URL returns HTTP 404 or 500, the protocol mandates immediate escalation to the methodologist, who consults the *official archive* (e.g., Wayback Machine for brand sites, PubMed Central for paywalled articles) and documents the archival source and capture date in the audit log.

## Stage 3: Screening and Eligibility Assessment

Screening applies the pre-registered inclusion/exclusion criteria in two sequential, independent phases—title/abstract and full-text—with dual human review and automated pre-filtering. In Phase 1 (Title/Abstract), all records from Stage 2 are loaded into a deduplicated database (e.g., Covidence, Rayyan). An automated script first applies hard exclusion rules (e.g., language ≠ English, publication year < 2018, document type = “editorial”) using metadata fields only; records failing these are auto-excluded with audit trail. The remaining records undergo dual, blinded screening by two trained reviewers using the protocol’s criteria. Disagreements are resolved by a third senior reviewer. In Phase 2 (Full-Text), only records passing Phase 1 proceed. Full texts are retrieved *only* from primary sources: journal articles via DOI-resolved publisher pages (e.g., `https://doi.org/10.1136/bmj.n71` → `https://www.bmj.com/content/372/bmj.n71`), product specs from official brand domains, and Amazon reviews from their canonical URLs. Reviewers assess against the same criteria, now applied to full content (e.g., “does the methods section describe randomization?”, “does the datasheet cite IEC 61960 testing?”). Per PRISMA 2020, “the flow diagram must report the number of records identified, included and excluded, and the reasons for exclusions” [1], and Cochrane requires “a record of all studies assessed for eligibility, including those excluded and the reasons” [2]. Human-in-the-loop checkpoints are embedded in both phases: the *blinded dual-review calibration* (conducted on a 50-record pilot set before main screening) ensures inter-rater reliability (Cohen’s κ ≥ 0.8), and the *disagreement resolution meeting* is mandatory for all conflicts. Output formats are strictly defined: (i) a versioned Markdown report (`screening_flow_v1.0.md`) containing the PRISMA 2020-compliant flow diagram (generated from templates at [prisma-statement.org](https://prisma-statement.org)) with counts and exclusion reasons [1]; (ii) a structured JSON file (`eligibility_decisions.json`) with one object per record, fields `record_id`, `phase` (“title_abstract” or “full_text”), `decision` (“include”, “exclude”, “uncertain”), `reason_code` (e.g., “EXCLUDE_LANGUAGE”, “EXCLUDE_METHODS_UNCLEAR”), and `reviewer_ids`; and (iii) an audit log (`screening_audit.json`) with timestamps, κ scores, and resolution notes. Failure handling addresses contradictory evidence: if reviewers find conflicting statements within a single source (e.g., a datasheet claims “1000 cycles” on page 3 but “500 cycles” in the footnote), the record is flagged as `uncertain`, escalated to the domain expert, and the discrepancy is resolved by consulting the *manufacturer’s official errata page* or contacting support—documented in the audit log.

## Stage 4: Data Extraction and Structuring

Data Extraction populates the pre-defined JSON Schema (`extraction_schema.json`) from Stage 1 with verified, atomic facts extracted directly from full-text primary sources. Extraction is performed using a hybrid approach: (a) rule-based automation for structured fields (e.g., parsing “N=120” from a methods section using regex, extracting “Battery Capacity: 5000 mAh” from a spec sheet with XPath), and (b) human review for unstructured or interpretive fields (e.g., “intervention description”, “user sentiment”, “risk-of-bias judgment”). All automation scripts are open-source, version-controlled, and include unit tests against known examples. For academic studies, extraction follows Cochrane’s “Risk of Bias 2” (RoB 2) tool for randomized trials, capturing domains like “bias arising from the randomization process” and “bias due to deviations from intended interventions” [2]. For product reviews, extraction captures verifiable claims (e.g., “battery lasted 18 hours”, “crashed 3 times in 2 days”) and contextual metadata (review date, star rating, verified purchase status). Per IEEE Std 1012, “data extracted for validation must be directly traceable to the requirement and the evidence” [3], so every extracted value includes a `source_span` (character offset range) and `source_url`. Human-in-the-loop checkpoints occur at three points: (i) *automation validation*, where two reviewers manually extract 20 records and compare outputs to script results, calculating precision/recall; (ii) *inter-rater reliability check* on 10% of human-extracted fields (Cohen’s κ ≥ 0.75); and (iii) *domain-expert sign-off* on all extracted values for high-stakes fields (e.g., clinical outcomes, safety-critical specifications). Output formats are: (i) a versioned Markdown report (`extraction_summary_v1.0.md`) summarizing extraction coverage, missingness, and key statistics; (ii) a structured JSON Lines file (`extracted_data.jsonl`) with one line per record, each containing all schema fields plus `source_url`, `source_span`, `extracted_by` (automated or reviewer ID), and `extraction_timestamp`; and (iii) an audit log (`extraction_audit.json`) with validation metrics and sign-off records. Failure handling addresses ambiguous extraction: if a field’s value is unclear (e.g., “improved significantly” without quantification), the extractor flags it as `NULL` with a `reason` (e.g., “NO_NUMERIC_VALUE_PROVIDED”) and escalates to the domain expert, who consults the *original study’s supplementary materials* or *manufacturer’s white paper* for clarification.

## Stage 5: Synthesis, Analysis, and Validation

Synthesis transforms extracted data into domain-specific, actionable insights using methods prescribed by the governing standard. For academic health evidence, synthesis follows Cochrane’s recommended approaches: meta-analysis for homogeneous RCTs (using RevMan Web), narrative synthesis for heterogeneous evidence, and “Summary of Findings” tables graded by GRADE methodology for certainty assessment [2]. For technical/product evidence, synthesis uses IEEE Std 1012’s “Verification Summary Report” structure, mapping extracted claims to requirements and assigning “Pass”, “Fail”, or “Inconclusive” based on evidence strength [3]. All analyses are performed in reproducible environments: R Markdown for statistical analysis (with `renv` lockfiles), Python Jupyter notebooks (with `papermill` for parameterized execution), or dedicated tools (RevMan Web, which exports XML). LLM-assisted validation is deployed *only* as a post-hoc checker: a fine-tuned model (e.g., `cochrane-robsummary-llm`) scans narrative syntheses for logical inconsistencies or unsupported claims, flagging them for human review—but never generates conclusions. Per PRISMA 2020, “authors should consider using tools such as GRADE to assess confidence in the body of evidence” [1]. Human-in-the-loop checkpoints are critical: (i) *analysis plan review* by a statistician/methodologist before running any model; (ii) *LLM flag triage* where all AI-generated flags are manually verified by two reviewers; and (iii) *final synthesis sign-off* by the domain expert and methodologist. Output formats are: (i) a versioned Markdown report (`synthesis_v1.0.md`) containing the narrative summary, forest plots (if meta-analysis), or verification tables, with all figures generated from code; (ii) a structured JSON file (`synthesis_results.json`) containing key metrics (e.g., `effect_size`, `95ci_lower`, `GRADE_certainty`, `verification_status`) and links to analysis code; and (iii) an audit log (`synthesis_audit.json`) with analysis timestamps, software versions, and sign-off records. Failure handling addresses contradictory evidence across sources: if studies/reviews conflict (e.g., “drug X reduces HbA1c by 1.2%” vs. “drug X shows no effect”), the synthesis explicitly models the heterogeneity (e.g., subgroup analysis by trial duration), cites the *original Cochrane Handbook guidance on handling disagreement* [2], and documents the reconciliation strategy in the audit log.

## Stage 6: Verification, Reporting, and Archiving

Verification is the final, independent quality assurance step, ensuring all prior stages comply with the registered protocol and governing standards. It is conducted by a verifier not involved in earlier stages, using a checklist derived directly from PRISMA 2020 (27 items), Cochrane Handbook (Chapter 12), and IEEE Std 1012 (Section 8). The verifier checks: (a) protocol adherence (e.g., “were all pre-specified sources searched?”, “were all exclusion reasons documented?”); (b) data integrity (e.g., “do extracted values match source spans?”, “are all audit logs complete?”); and (c) reporting completeness (e.g., “is the PRISMA flow diagram present and accurate?”, “are GRADE assessments included?”). Any deviation triggers a *verification incident report*: the issue is logged in `verification_audit.json` with severity (Critical, High, Medium), root cause, and required corrective action (e.g., “re-run extraction for 5 records”, “add missing GRADE assessment”). Critical issues halt release until resolved. Reporting produces the final deliverables: a comprehensive, versioned Markdown report (`final_report_v1.0.md`) integrating all prior outputs with executive summaries tailored to the Target Audience, and a machine-readable JSON bundle (`research_bundle_v1.0.json`) containing all stage outputs, metadata, and checksums. Archiving follows FAIR principles: the entire project (code, data, reports, audit logs) is deposited in a trusted repository (e.g., Zenodo) with a DOI, licensed under CC BY 4.0 (per PRISMA’s license [1]), and linked to the original protocol DOI. Human-in-the-loop checkpoints are: (i) the *independent verification* itself, and (ii) the *final release sign-off* by the project lead and verifier. Output formats are: (i) the final report and bundle; (ii) a `verification_report_v1.0.md` detailing all checks passed/failed; and (iii) the comprehensive `verification_audit.json`. Failure handling addresses unresolved contradictions: if verification uncovers irreconcilable errors (e.g., fabricated data), the report is withdrawn, the incident is documented per institutional ethics guidelines, and the audit log is preserved immutably.
