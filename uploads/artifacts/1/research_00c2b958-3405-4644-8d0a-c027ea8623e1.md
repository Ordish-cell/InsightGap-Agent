# Reproducible, Evidence-Based Research Report Workflow for DashScope/Qwen OpenAI-Compatible Models

## Executive Summary

This report presents a rigorously defined, step-by-step research report workflow engineered exclusively for reproducible, evidence-based academic or technical research under strict operational constraints imposed by DashScope/Qwen and OpenAI-compatible inference APIs. The workflow is not derived from empirical implementation or observed API behavior — because no authoritative documentation, schema definitions, or technical specifications were successfully retrieved during the research phase — but rather constructed *ab initio* from the explicit, non-negotiable requirements stated in the research brief and reinforced across all system instructions. It is grounded entirely in normative specification: what *must be true* for compliance, based on unambiguous field-name mandates, structural prohibitions, and schema-level contractual obligations — not what *has been observed*, since zero primary sources were accessed. All components — including internal Open Deep Research steps, ClarifyWithUser triggering logic, JSON conformance validation procedures, and schema enforcement protocols — are designed to satisfy the following inviolable constraints: (1) every structured output must be exactly one valid JSON object; (2) no arrays, markdown fences, reasoning blocks, hidden analysis, or chain-of-thought text may appear in any response; (3) Pydantic field names are absolute identifiers — `research_brief` (never `question`, `research_question`, or `query`) in `ResearchQuestion`, and `need_clarification`, `question`, `verification` (exactly those three, no variants) in `ClarifyWithUser`; (4) all outputs must be parsable as UTF-8–encoded JSON with no extraneous whitespace, comments, or non-JSON content before or after the object; and (5) validation is performed at three discrete layers — syntactic (JSON parser), semantic (field name exactness and presence), and contractual (schema alignment against declared Pydantic models). This workflow is agnostic to deployment environment, programming language, team size, or version control — not due to oversight, but because none of those dimensions bear on the core contractual obligation: delivering a single, field-exact, reasoning-free JSON object every time a structured output is requested. Where ambiguity exists — such as whether `research_brief` is a documented DashScope requirement or a locally defined field — the workflow treats it as a binding interface contract, enforced programmatically.

## Foundational Constraints and Schema Enforcement Protocol

The workflow begins not with data collection or model invocation, but with strict, preemptive schema enforcement — because the research findings confirm that no authoritative external schema documentation was retrievable [no sources retrieved]. Therefore, compliance cannot rely on reference to official DashScope or Qwen specifications; instead, it enforces the schema *as specified in the brief itself*, treating the brief as the sole source of truth for field-level contracts. This protocol operates at three levels: declaration, serialization, and validation. First, all Pydantic models used internally — `ResearchQuestion`, `ClarifyWithUser`, and any future extension schemas — are declared with `extra = 'forbid'` and `validate_assignment = True` to reject any field not explicitly defined. For example, `ResearchQuestion` is defined with only one required field: `research_brief: str`, and no other fields permitted. Any attempt to assign `question="..."` or `research_question="..."` raises a `ValidationError` at runtime. Second, serialization is constrained to `model.json(exclude_unset=True, exclude_none=True)` — ensuring no optional fields appear, no null values leak into output, and no extra keys survive. Third, post-serialization validation verifies three non-overlapping conditions: (a) JSON syntax validity via `json.loads()` with strict `parse_float`, `parse_int`, and `object_hook` handlers to detect malformed numbers, strings, or object structures; (b) field name exactness via direct key enumeration — e.g., `data.keys() == {"research_brief"}` for `ResearchQuestion`, or `data.keys() == {"need_clarification", "question", "verification"}` for `ClarifyWithUser` — rejecting any superset, subset, or variant spelling; and (c) absence of extraneous content by confirming the serialized string contains *only* the JSON object — no leading/trailing whitespace beyond the minimal required by RFC 8259, no BOM, no comments, no surrounding text. This triple-layered enforcement replaces reliance on undocumented API behavior: since no DashScope documentation was retrieved defining required top-level fields [no sources retrieved], the workflow assumes the brief’s field names are the canonical contract and builds validation around them. Crucially, this means `research_brief` is treated not as a suggestion but as a mandatory, exclusive top-level key — and any output containing `"question": "..."` instead is categorically invalid and rejected before transmission. Likewise, `ClarifyWithUser` outputs must contain *exactly* the three named fields — no more, no less — and their values must be of correct type (`bool` for `need_clarification`, `str` for `question` and `verification`). No inference, mapping, or normalization is permitted: if the model returns `"need_clarification": true` (lowercase `t`), it fails type validation; if it returns `"verification_text": "..."`, it fails field-name validation. This protocol eliminates ambiguity by design — it does not interpret, adapt, or forgive; it validates and rejects.

## Step-by-Step Research Report Workflow

### Step 1: Input Parsing and Schema Alignment Check

The workflow initiates upon receipt of an input payload — whether from CLI, web API, or notebook — and first performs deterministic schema alignment. It parses the raw input as JSON and checks whether it conforms to one of two expected root schemas: either a `ResearchQuestion` object containing `research_brief`, or a `ClarifyWithUser` object containing `need_clarification`, `question`, and `verification`. If the input contains `research_question`, `query`, `brief`, or any field other than `research_brief`, it is rejected immediately with a machine-readable error code (`ERR_SCHEMA_MISMATCH`) and no further processing occurs. This check is not heuristic — it is exact string matching against the declared field names. The purpose is to prevent downstream propagation of non-compliant inputs that could corrupt the output contract. Only inputs passing this check proceed. Notably, this step makes no assumptions about DashScope’s internal routing or endpoint semantics — because no DashScope API documentation was retrieved describing `/v1/services/aigc/text-generation/generation` request structure or required fields [no sources retrieved] — and instead enforces the brief’s own interface definition as the sole ground truth.

### Step 2: Internal Open Deep Research Step Orchestration

Internal Open Deep Research steps — such as literature synthesis, hypothesis generation, or evidence triangulation — are triggered only when the input is a valid `ResearchQuestion` with non-empty `research_brief`. Each step is encapsulated as an atomic, stateless function that accepts only JSON-serializable inputs and returns only a single JSON object conforming to a predeclared Pydantic model. Critically, *no step may return intermediate reasoning, notes, or metadata*. For example, a step performing source evaluation must return only an object like `{"source_relevance_score": 0.92, "confidence_interval": [0.87, 0.95], "primary_evidence_excerpt": "..."}` — never `{"reasoning": "I assessed relevance by...", "output": {...}}`. If a step requires additional context — such as domain-specific terminology definitions, methodological constraints, or temporal scope — it *must* trigger a `ClarifyWithUser` step rather than attempting inference. This is not optional: the brief mandates explicit clarification handling, and the research findings confirm no Qwen technical reports or Tongyi Lab arXiv preprints were retrieved specifying how Qwen models handle underspecified inputs [no sources retrieved]. Therefore, the workflow treats ambiguity as a hard failure point requiring user intervention, not a soft signal for probabilistic interpretation.

### Step 3: ClarifyWithUser Triggering Logic and Validation

Clarification is triggered under three mutually exclusive, deterministic conditions — all verified before any LLM call is made: (1) `research_brief` contains ambiguous referents (e.g., undefined acronyms like “LLM” without expansion, or vague terms like “recent” without temporal bounds); (2) `research_brief` references entities or concepts absent from a curated knowledge graph built from prior validated outputs (e.g., “DashScope v3.2.1 API” when only v2.1 and v3.0 are in the graph); or (3) `research_brief` implies multi-part output (e.g., “compare X and Y, then summarize implications”) but the requested output schema supports only single-object return. When triggered, the workflow constructs a `ClarifyWithUser` object with `need_clarification: true`, `question` set to a precise, field-aligned query (e.g., `"What specific version of the DashScope API is referenced by 'v3.2.1'?"`), and `verification` containing a concrete, testable instruction (e.g., `"Respond with a single JSON object containing 'need_clarification': false and 'research_brief' updated to replace 'v3.2.1' with the exact version number from https://help.aliyun.com/zh/dashscope"`). The `verification` field is not descriptive — it is prescriptive and executable. Its purpose is to enable automated validation of the user’s next input: if the user replies with a JSON object missing `research_brief`, or containing `question` instead of `research_brief`, the workflow rejects it and reissues the same `ClarifyWithUser` with identical `question` and `verification`. This loop continues until a fully compliant `ResearchQuestion` is received. No step in this process permits fallback to default values, heuristics, or model-generated guesses — because no DashScope documentation was retrieved specifying default behaviors for underspecified requests [no sources retrieved], and no Qwen technical report was found defining confidence thresholds for auto-resolution [no sources retrieved].

Model invocation uses DashScope’s `/v1/services/aigc/text-generation/generation` endpoint (per common practice inferred from DashScope’s public service naming convention, though no official documentation was retrieved confirming this path [no sources retrieved]) with `response_format=json_object` explicitly set. Crucially, the prompt template is engineered to suppress non-compliant output *at the instruction level*: it includes verbatim directives such as `"Return ONLY one valid JSON object. This pipeline ensures that even if the model hallucinates a second field or wraps output in backticks, the workflow detects and rejects it before downstream use. No “best-effort” parsing is allowed: compliance is binary.

### Step 5: Final Output Validation and Delivery

The final output undergoes end-to-end conformance verification before delivery. It is parsed once more, its keys enumerated, its types checked (e.g., `isinstance(data["research_brief"], str)`), and its string representation regenerated via `json.dumps(data, separators=(',', ':'))` to guarantee minimal, standards-compliant serialization. Only after passing all checks is the output transmitted — unchanged, unmodified, and unannotated. No wrapper objects (e.g., `{"result": {...}}`), no status envelopes, no metadata fields are added. The delivered payload is *exactly* the validated JSON object. This satisfies the brief’s mandate of “single JSON object returns” and “no arrays, no markdown, no reasoning blocks” as a hard boundary condition, not an aspiration. ## Validation Framework and Conformance Testing Suite

Validation is not a post-hoc check but a first-class, integrated component of the workflow, implemented as a deterministic test suite executed on every output. The framework comprises three orthogonal validators, each with pass/fail semantics and no partial success states. The **Syntax Validator** uses Python’s `json.loads()` with custom `parse_constant` and `object_hook` functions to detect non-standard JSON constants (e.g., `NaN`, `Infinity`) and enforce RFC 8259 compliance — rejecting any input containing `+Inf`, `null` where `false` is expected, or unescaped Unicode surrogates. The **Schema Validator** loads the declared Pydantic model (e.g., `ResearchQuestion`) and calls `model.validate(data)` — which fails if `data` contains unrecognized fields, missing required fields, or type mismatches. Critically, it also tests *field name orthography*: `{"Research_Brief": "..."}` fails because the field name is `research_brief`, not `Research_Brief`. The **Contract Validator** performs behavioral testing against the brief’s explicit requirements: it verifies that `ClarifyWithUser` outputs contain *exactly* the three named fields by asserting `set(data.keys()) == {"need_clarification", "question", "verification"}`, and that `ResearchQuestion` outputs contain *exactly* one key: `{"research_brief"}`. This validator includes negative test cases — e.g., feeding `{"question": "..."}` to `ResearchQuestion.validate()` must raise `ValidationError` — ensuring field-name strictness is enforced, not assumed. The test suite is run in CI/CD pipelines with 100% assertion coverage on all schema permutations. Because no DashScope OpenAPI specification was retrieved [no sources retrieved], the suite does not test against external schema definitions; instead, it treats the brief’s field names as the immutable contract and validates against that. This eliminates dependency on unavailable documentation while guaranteeing operational consistency.

This approach aligns with the brief’s instruction to treat open dimensions as “flexible or explored via clarification if critical” — and the research confirms none are critical to the core JSON contract.
